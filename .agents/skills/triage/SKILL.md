# Triage

Move Linear issues through the workflow. Workspace, team key (`MAE`), and MCP usage are in
`docs/agents/issue-tracker.md`.

Every comment or issue you post during triage **must** start with this disclaimer:

```
> *This was generated by AI during triage.*
```

## Reference docs

- [AGENT-BRIEF.md](AGENT-BRIEF.md) — how to write durable agent briefs
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md) — how the `.out-of-scope/` knowledge base works

## Workflow states

Lifecycle is the Linear workflow state. Never add a label that restates it.

- **Triage** — the inbox. Nobody has evaluated it yet.
- **Backlog** / **Todo** — evaluated and accepted, waiting to be picked up.
- **In Progress** — being worked on.
- **Done** — shipped.
- **Canceled** — will not be actioned.

Moving an issue out of Triage **is** triaging it. Never create a new workflow state — states are
workspace-level and affect every board. If a distinction is missing, add a label instead.

## Labels

**Category** — exactly one:

- `Bug` — something is broken
- `Feature` — new capability the app doesn't have
- `Improvement` — an existing capability made better, extended, or refined. Includes visual and copy
  refinement of something that already works.
- `Maintenance` — internal work with no user-visible change: dependency bumps, refactors, tooling,
  tests, CI, migrations

Three questions settle every case:

- **Does it misbehave?** Then `Bug`. If it behaves correctly but could be better — including looking
  or reading better — it's `Improvement`.
- **Is the capability there at all?** If not, `Feature`. If it exists and is being made better,
  `Improvement`.
- **Would anyone outside the repo notice?** If not, `Maintenance`, whatever else it resembles.

**Readiness** — at most one, orthogonal to state:

- `Needs Info` — waiting on the reporter
- `Ready for Agent` — fully specified, an AFK agent can pick it up unattended
- `Ready for Human` — needs judgment, external access, design decisions, or manual testing

`Needs Info` and `Ready for Agent` contradict each other. If both are set, flag it and ask the
maintainer before doing anything else.

## Transitions

- An issue in **Triage** goes to **Backlog**/**Todo** with a readiness label, or to **Canceled**, or
  stays in Triage carrying `Needs Info` while you wait on the reporter.
- When the reporter answers, drop `Needs Info` and re-evaluate.
- The maintainer can override anything. Flag transitions that look unusual and ask first.

## Invocation

The maintainer invokes `/triage` and describes what they want in natural language. Interpret and act:

- "Show me anything that needs my attention"
- "Let's look at MAE-42"
- "Move MAE-42 to `Ready for Agent`"
- "What's ready for agents to pick up?"

## Show what needs attention

Query Linear and present three buckets, oldest first:

1. **In Triage** — never evaluated.
2. **`Needs Info` with reporter activity since your last triage comment** — needs re-evaluation.
3. **In Backlog/Todo with no readiness label** — accepted but never specified, so nobody can pick it up.

Show counts and a one-line summary per issue. Let the maintainer pick.

## Triage a specific issue

1. **Gather context.** Read the issue in full — description, comments, labels, state, reporter, dates.
   Parse any prior triage notes so you don't re-ask resolved questions. Explore the codebase using the
   relevant `CONTEXT.md` glossary, respecting ADRs in the area. Read `.out-of-scope/*.md` and surface
   any prior rejection that resembles this issue.

2. **Recommend.** Give the maintainer your category label, readiness label, and target state with
   reasoning, plus a brief codebase summary relevant to the issue. Wait for direction.

3. **Reproduce (`Bug` only).** Before any grilling, attempt reproduction: read the reporter's steps,
   trace the relevant code, run tests or commands. Report what happened — successful repro with the
   code path, failed repro, or insufficient detail, which is a strong `Needs Info` signal. A confirmed
   repro makes a much stronger agent brief.

4. **Grill (if needed).** If the issue needs fleshing out, run a `/grill-with-docs` session.

5. **Apply the outcome:**
    - **`Ready for Agent`** → Backlog or Todo, add the label, post an agent brief comment
      ([AGENT-BRIEF.md](AGENT-BRIEF.md)).
    - **`Ready for Human`** → same, with a brief noting why it can't be delegated.
    - **`Needs Info`** → leave it in Triage, add the label, post triage notes (template below).
    - **Canceled, a `Bug`** → polite explanation, then move to Canceled.
    - **Canceled, a `Feature` or `Improvement`** → write to `.out-of-scope/`, link it from a comment,
      then move to Canceled ([OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)).
    - **Canceled, `Maintenance`** → comment why and move to Canceled. No `.out-of-scope/` entry;
      dropped internal work is not a scope decision.
    - **Accepted but not yet specified** → Backlog with the category label and no readiness label.
      Comment only if there's partial progress worth recording.

## Quick override

If the maintainer says "move MAE-42 to `Ready for Agent`", trust them and do it. Confirm what you're
about to change — state, labels, comments — then act. Skip grilling. If you're applying
`Ready for Agent` without a grilling session, ask whether they want an agent brief written.

## `Needs Info` template

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

Capture everything resolved during grilling under "established so far" so the work isn't lost.
Questions must be specific and actionable, not "please provide more info".

## Resuming a previous session

If prior triage notes exist on the issue, read them, check whether the reporter answered any
outstanding questions, and present an updated picture before continuing. Don't re-ask resolved
questions.
